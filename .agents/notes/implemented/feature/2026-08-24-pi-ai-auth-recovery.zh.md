# Agent Note: pi-ai 内容前认证恢复

Status: implemented

[English](2026-08-24-pi-ai-auth-recovery.md) | 中文

## 问题

OAuth 提供方可能拒绝一个按它自己的记录仍然有效的令牌。Codex 部署展示了具体形态：DSH 存储自己的 OAuth 凭据，共享同一 ChatGPT 会话的另一个客户端刷新并轮转了令牌族，随后约九十秒内后端对已存储的访问令牌返回 401。pi-ai 的 `resolveStoredOAuth` 只在存储的过期时间过后才刷新，因此没有触发刷新；适配器把终止错误归类为 `AUTH`；`dsh-llm-retry` 的默认可重试代码里没有 `AUTH`，于是轮次在第一次尝试就失败，连续三次，直到后来某次重试恰好落在后端窗口关闭之后。一次瞬时的认证后端拒绝变成了三次用户可见的轮次失败，且没有任何自动恢复。

## 决定

`@deepseek-ai/dsh-llm-pi-ai` 在适配器内部恢复内容之前的认证拒绝，按提供方路由通过新的 `authRecovery` profile 字段配置（`retries` 默认为 1，`delayMs` 默认为 1000；`retries: 0` 表示禁用）。当流的终止失败在任何块到达调用方之前归类为 `AUTH` 时，适配器会捕获被拒绝的已存储凭据，并通过凭据存储的 `modify` 在记录仍然匹配时刷新它——这与 pi-ai 自己的刷新运行在同一互斥之下。因此，并发恢复若已轮转记录，重试会直接使用新令牌而不会再次刷新。API 密钥覆盖不会轮转无关的已存储 grant。重试会从存储重新解析认证、等待配置的延迟，然后重放请求。

恢复逻辑位于 [`src/adapter.ts`](../../../../packages/llm/llm-pi-ai/src/adapter.ts)，是一个围绕抽取出的单次尝试生成器的尝试循环。末尾的 `usage` 块会被多保留一步，因此被放弃尝试的计数永远不会到达调用方，而成功或预算耗尽的尝试仍然先发出 `usage` 再发出 `finish`。强制刷新失败不会阻止重试：令牌端点故障并不能说明资源端点是否仍拒绝已存储的凭据，因此由重试的请求来回答这个问题。每次尝试专用的 pi-ai 集合会记录其惰性认证实际提供的已存储凭据，路由的整数 `streamIdleTimeoutMs` 同时约束凭据存储串行化和刷新网络调用。插件把 `onAuthRecovery` 观察者接到日志器上，使整个恢复周期在宿主日志中可见（[`src/index.ts`](../../../../packages/llm/llm-pi-ai/src/index.ts)）。

### 为什么只在内容之前

一旦已有任何块流出，重放请求会重复循环可能已经持久化的内容，因此流中段的认证失败会原样到达轮次层。401/403 实际上总是在内容之前到达——状态行先于正文——因此这一限制在已观察到的情形中不损失任何东西，并保持与 `dsh-llm-retry` 的“失败的块不进入派生消息”规则相同的重试语义。

### 为什么在适配器而不是重试插件

`dsh-llm-retry` 在已关闭步骤的扩展点上执行：轮次级重试会重建整个请求、重新计费全部上下文，并开启一个新的编号轮次。认证恢复需要轮次级重试根本做不到的事情——在 pi-ai 的过期检查触发之前强制刷新凭据——而常见情形（令牌族轮转、后端瞬时故障）只需一次廉价重发即可恢复。想要第二道防线的部署仍可在 profile 的 `retryPolicy.retryableCodes` 中加入 `AUTH`；两层可以组合，因为耗尽的适配器恢复会照旧把 `AUTH` 抛到上面。

## 备选方案

- **把 `AUTH` 列为 `dsh-llm-retry` 的默认可重试代码**——否决：它会以轮次粒度重试每个提供方家族，每次尝试都重发全部上下文，并且仍然无法刷新 pi-ai 认为未过期的凭据。需要的部署可按 profile 自行开启。
- **每次 401 只刷新不重试**——否决：令牌端点暂时不可达的刷新会让本来有效的凭据搁浅，而纯后端瞬时故障并不需要轮转；重试同时覆盖两种情形。
- **在 pi-ai 内部拦截（上游补丁）**——否决：pi-ai 在适配器看到错误之前就把提供方错误压平为消息文本，而 Harness 持有的凭据存储才是持久化轮转的正确位置；上游改动两者都看不到。
- **在其他客户端轮转令牌族时主动刷新**——否决：没有任何信号可依附；401 是最早可观察的事实。

## 后果

内容之前的 401/403 在轮次可能以 `AUTH` 失败之前，代价是一次刷新调用、一段配置的延迟和一次额外请求；想要旧行为的部署可设置 `authRecovery: { retries: 0 }`。API 密钥路由获得不带刷新的重试（没有可轮转的东西），这覆盖了纯认证后端瞬时故障。本次没有修复的情形：真正失效的刷新令牌仍会以 `invalid_grant` 失败，重试也会失败，该路由需要重新登录——但现在可以通过 `onAuthRecovery` 日志行观察到，而不是一个无法解释的裸 `AUTH`。

## 测试

`packages/llm/llm-pi-ai/tests/auth-recovery.spec.ts` 通过脚本化 HTTP mock 驱动真实组合：401 后成功的透明恢复、预算耗尽后抛出 `AUTH`、`retries: 0` 禁用、多次尝试预算、留给轮次层的非认证失败、一次强制 OAuth 刷新轮转已存储凭据并使下一次请求携带新的 bearer 令牌、捕获请求期 OAuth 轮转、并发轮转抑制重复刷新、API 密钥与无密钥非 OAuth 隔离、受 idle 超时约束的生产凭据存储获取和令牌端点调用、取消阻止迟到的持久提交，以及刷新失败后仍落到重试。`config.spec.ts` 固定解析后的默认值与无效预算的写入时拒绝。现有的 401 适配器测试现在会为重试的第二次请求编写脚本。没有快照 fixture：模型可见的内容没有任何变化——恢复的尝试是同一个请求——失败路径的 transcript 表面也不变。
