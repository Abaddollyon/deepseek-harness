# Agent Note: 公共拉取请求 CI 使用托管运行器

Status: implemented

[English](2026-09-10-public-hosted-ci.md) | 中文

## 问题

拉取请求的合并引用可以携带贡献者控制的工作流修改。选择私有运行器的工作流表达式不能建立安全边界，而私有容量不可用会导致必需的汇总结果无法运行。标准托管运行器的容量也低于 CI 并发工作负载所依据的大型运行器池。

## 决策

[拉取请求 CI](../../../../.github/workflows/ci.yml) 仅使用标准 GitHub 托管运行器，包括 Node 兼容性矩阵和必需的汇总任务。基准测试保留固定的托管镜像，可复用的 Python 运行时构建器保留托管平台矩阵。故障切换变量不选择拉取请求运行器。本决策取代[故障切换运行手册](2026-07-26-ci-failover-runbook.zh.md)中的主 CI 拉取请求路由，以及 [Node 兼容性决策](2026-09-06-node-compatibility-selfhosted.zh.md)中的私有池选择；发布演练工作流不在本次变更范围内。

管理员必须禁止公共仓库访问私有运行器组。贡献者可以修改拉取请求工作流，因此其中的托管标签或仓库条件都不能替代运行器服务的访问策略。

[Master CI](../../../../.github/workflows/ci-master.yml) 保留两个完整、未分片的私有待命聚合检查。它们仅在私有仓库的 master 推送时运行，且该仓库的 `DSH_CI_PRIVATE_RUNNER_REPOSITORY` 变量必须等于完整的 `github.repository` 名称。未设置或不匹配的变量使任务在分配运行器前跳过。这是显式调度启用，而非运行器授权。托管 master 平台检查和独立限定范围的 [fork master 门禁](../../../../.github/workflows/ci-fork-master.yml)无需该启用即可运行。

托管门禁及其嵌套的浏览器、快照、lint 和包验证并发一并受到限制。覆盖率使用两个插桩分区进程与一个重型豁免 worker 并行运行；只降低 `DSH_COVERAGE_MAX_WORKERS` 不会改变分区数量。清单、阈值、测试期限和必需汇总依赖保持不变。缓存恢复和浏览器系统依赖安装依据 `runner.environment`，而不是故障切换变量。只恢复不写入的包缓存与浏览器缓存保留其现有冷启动限制。

## 考虑过的替代方案

**在 YAML 中为可信拉取请求选择私有运行器。** 拒绝，因为贡献者控制的工作流表达式不能建立信任。私有 PR（Pull Request）故障切换需要独立强制执行的访问策略，本工作流不提供此能力。

**移除 master 待命任务。** 拒绝，因为完整串行聚合检查为独立运营的私有池提供就绪证据。显式启用私有仓库既保留该证据，也避免公共仓库在不可用的池上排队。

**保留大型运行器并发或削弱覆盖率。** 拒绝，因为过多的并行进程争抢标准托管 CPU 和内存，而缩减清单或阈值会删除验证，并非限制验证的资源使用。

## 影响

拉取请求检查不再依赖私有池的可用性，但不能通过主 CI 故障切换变量绕过托管服务故障。保守并发可能增加耗时；托管 CI 仍负责在其实际资源上验证完整工作负载。私有池操作员必须显式启用，并在这些工作流文件之外维护运行器组访问限制。

[工作流测试](../../../../scripts/ci-workflow.spec.ts)检查所有直接拉取请求任务和 Node 矩阵的运行器标签、基于实际运行器的缓存与浏览器条件、固定托管预算、必需汇总输入，以及私有待命任务的事件、可见性与启用场景。这些配置检查不能证明实际运行器权限或工作负载性能。
