# Agent Note: 工作流终态成员保持可导航

Status: implemented

[English](2026-08-25-workflow-terminal-member-navigation.md) | 中文

## 问题

持久工作流 Chat 节点中的成员行此前只有在成员的持久状态与列表行都仍处于运行中时，才能打开其子 Session。成员一旦完成、失败或被中断，其行就变为静态——即使子 Session 通常仍在普通 Session 列表中，且 `sessions.open(id)` 对已结束的子级与运行中的子级同样有效。复盘一次已结束的运行（持久运行记录的主要用途）因此只能去 Session 侧栏里手动找子级。

这个门槛还有第二层不幸：运行记录会把已关闭位置中缺少结果的成员投影为 `interrupted`——进程停止会让所有仍在运行的成员同时变为静态，而这恰恰是用户最需要检查每个子级进展的时刻。

## 决策

`ui-workflow-run` 的 `WorkflowRunPanel` 中的 `navigableMembers()` 不再以生命周期为门槛。只要普通 Session 列表包含成员的子 id、行为 `origin: 'subagent'` 且 `parentId` 等于所展示的父级，成员即可导航——这三项身份证明保持不变。成员的持久状态与列表行的 `running` 标记不再参与：它们描述的是工作是否存活，而不是子 Session 能否打开。

本决定部分取代 [Chat 中的持久工作流运行](../feature/2026-08-10-durable-workflow-runs-in-chat.zh.md)，后者曾以“工作流记录证明历史身份而非当前可访问性”为由拒绝终态导航。该异议由门槛保留的另一半回答：可访问性来自当前普通列表，而非记录。列表包含的行通过与侧栏相同的注入 `sessions.open(id)` 打开；列表不包含的行（远程、仅地址化或父级不符）保持静态，因此本节点仍不提供冷 Session 或跨远程的打开承诺。

`MemberRow` 的聚焦成员保留机制不变，但其触发条件改变了：聚焦按钮现在是在子行离开普通列表时失去可导航性，而不是在成员结算时。

## 曾考虑的替代方案

- **保留运行中门槛。** 拒绝：它让持久记录自相矛盾——最值得复盘的成员（已完成、已中断）恰恰是无法打开的，而真正保证打开安全的身份证明原本就已在执行。
- **把可导航性持久化进运行记录**（例如在成员结束时写入 `openable` 标记）。拒绝：导航必须跟随当前列表事实而非历史；持久化的“是”会让已删除或被过滤的子级错误地保持可交互，而持久化的“否”在列表行回归后也永远无法撤销。

## 后果

完成、失败、已取消和已中断的成员在其普通列表行存在期间（包括页面刷新后）都可以打开其子 Session。导航仍会随列表事实消失——行离开普通列表后成员恢复为静态文字——因此 [状态驱动的工作流 disclosure](../feature/2026-08-11-workflow-run-status-driven-disclosure.zh.md) 中的延迟关闭推理保留其机制，只是触发条件改变了。

组件测试覆盖：一个已完成成员与一个已中断成员打开各自已结算的子级，以及没有子 Session 行的成员保持静态；shipped Web 回放现在断言结算后的成员是可打开子级的按钮（实时与刷新后两种路径），此前它断言的恰恰相反。
