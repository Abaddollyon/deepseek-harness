# Agent Note：实时事件重新打开出错的会话窗口

Status: implemented

[English](2026-08-25-live-event-window-recovery.md) | 中文

## 问题

只要历史请求失败——传输故障、超时，或主机繁忙无法应答——`Session.doOpen` 就会停在 `openState: 'error'`。此后 `acceptLiveEvent` 会丢弃每一个后续帧：窗口从未装载，没有可追加的位置，而历史本应在下次打开时补齐。但没有任何代码去安排那次打开。只有 `resync()` 会重建出错的窗口，而它只在重连时运行；于是一个传输始终正常、仅有那一次历史请求失败的会话，会持续收到实时帧并全部丢弃。用户看到对话冻结在最后一次正常状态，而持久日志仍在推进，只有刷新浏览器才能恢复——这也正是它看起来像渲染问题而非窗口丢失的原因。

这个故障需要负载才会出现，而不是别处的缺陷：在繁忙主机上，大会话的首次历史请求是打开路径中最慢的调用，因此它最先失败，也是唯一一个失败后不可恢复的调用。

## 决定

窗口处于出错状态时到达的实时帧，现在会重新打开窗口，而不是被丢弃。到达本身就是重试所需的证据：帧经由 mux 流传输，因此一个帧的到达即证明传输已恢复，先前失败的历史请求现在可以成功。

该帧刻意不做缓冲。重建会拉取尾页，其中已经包含它；而向一个可能永远无法装载的窗口缓冲，才是真正会泄漏的做法。请求在途期间 `open()` 是幂等的，因此一批帧最多触发一次重试；重试再次失败也只是让状态保持原样——下一个帧再试一次即可。

`'cold'` 保持原有语义，不受影响：从未打开过的会话没有窗口可重建，其历史确实会在被打开时补齐。

## 备选方案

**定时重试。** 否决：在传输已死时白白消耗请求，在传输正常时又要空等一个周期，而证明恢复的那个帧其实已经在手中。

**缓冲这些帧，等最终打开时缝合。** 否决：重试本就会拉取历史，缓冲只是重复页面已携带的内容；而永不重开的出错窗口会让缓冲无界增长。

**改为暴露一个重试控件。** 作为主要修复被否决：那是把瞬时故障推给用户。可见的错误状态仍有价值，但它应与自动恢复并存，而非取而代之。

## 验证

`packages/client/runtime/tests/session.client.spec.ts` 驱动一次失败的历史请求，断言窗口停在 `'error'`，随后在传输正常的情况下投递一个实时帧，断言窗口到达 `'open'` 且记录到第二次历史调用。没有此改动该用例失败：窗口保持出错，且不会发出第二次请求。

## 影响

会话能在传输自证可用的那一刻自行从瞬时历史失败中恢复，无需刷新，也无需重连。确实无法加载的会话——日志被删除或不可读——仍会停在 `'error'`；此后每个帧只付出一次重试，其频率受主机本就在为该会话维持的帧率约束。
