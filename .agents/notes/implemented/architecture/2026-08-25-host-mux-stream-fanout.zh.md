# Agent Note：主机 mux 流式传输——单一扇出监听器与被取代的投影帧

Status: implemented

[English](2026-08-25-host-mux-stream-fanout.md) | 中文

## 问题

每条打开的 mux 流都会安装自己的 `ctx.on('session/event')` 监听器，而每个监听器都会为同一个事件重新推导出同一个帧：维护私有的未决调用表、经 `ctx.agents` 解析呈现器作用域、运行 `viewFor`、铸造自己的信封。于是这份工作被连接的消费者数量放大——同一主机上两个浏览器标签页要为每个会话事件付两遍代价，八个就是八遍——尽管它们收到的内容完全相同。

另外，mux 队列是一个无界 FIFO，没有任何丢弃策略，因此尚未排空的消费者仍会收到整值推送帧的每一个中间值。

`apps/web/tests/host-fanout.perf.ts`（perf 泳道，`pnpm run test:web:perf`）按真实部署的基数为两者定价——1,561 个会话、一个增长到 1,724 事件以上的对话、一次 1,320 事件的突发，以及 1/2/4/8 条并发 mux 流。改动之前，扣除纯 `session.append` 基线后的扇出开销随流数线性增长：

| 流数 | 1 | 2 | 4 | 8 |
|---|---|---|---|---|
| 每次 1,320 事件突发的扇出毫秒数 | 51 | 90 | 170 | 348 |

对 8 流突发的 CPU 剖析显示，354ms 中有 106ms 归属于从每流监听器体内直接触达的 Cordis Context 属性代理——即急切求值的 `ctx.agents.get(session.id)` 实参——另有 26ms 属于 `viewFor` 内部的同一代理。即便只算一次，这些查找中也有四分之三是浪费：只有 `tool/call` 与 `tool/result` 可能携带视图，而作用域却对每种事件类型都被解析。

帧普查暴露了第二项开销。按每条流计，那次 1,320 事件的突发投递了 1,520 个 `session/projection` 帧——帧数多于事件数，因为 token-meter 的各单元几乎在每个事件上都会重算。

## 决定

**一个进程级 `session/event` 监听器。** 未决调用表、视图计算与信封铸造移至网关作用域；监听器把一个共享信封推送给 `muxQueues` 中的每个队列，这正是 `broadcast` 对其他所有推送帧已有的做法。共享信封是安全的，因为 mux 消费者只在可应答帧上读取 `rpcId`，而那些帧在待决登记表中铸造自己的稳定 id。各条流保留自己的 `session/created` 与任务监听器；那些是每流基线，而非每事件工作。

该表现在从网关启动起就是热的，而不再是每次开流时为空，因此中途打开的流会从表中解析结果的调用配对，而不是走回扫兜底。两条路径返回相同的配对。

**惰性呈现器作用域。** `viewFor` 接受 `scopeFor: () => ScopeKey | undefined` 而非已解析的 `ScopeKey`，与它旁边的 `argsFor` 参数对称。代理查找现在只对可能产生视图的那两种事件类型发生。

**`FrameQueue` 中的取代键合并。** 队列可以带一个键函数构造。当带该键的未投递帧仍在缓冲中时，更新的帧会就地清空较旧的槽位，因此较旧的帧永不投递；清空而非拼接删除，保持了其他每个帧的队列位置，也因而保持了所有跨键顺序。`muxSupersedingKey` 是"哪些种类符合条件"的唯一归属处，而它**只**为 `session/projection` 设键。

## 为何只有 `session/projection`

只有当后续帧能重建被丢弃帧所携带的全部内容时，才可以丢弃一个帧。`session/projection` 在两个要点上都成立。它携带某个单元完整的最终值，外加计算时所处的水位 `seq`，而客户端投影存储的应用规则就是 `seq <= current ? ignore : replace`——因此在本队列中被超越的帧，恰恰就是客户端在收到时也会自行丢弃的帧。它同时也是唯一有足够体量来支撑该机制的种类。

其他每一种都不设键。`session/event` 是唯一的持久日志条目，丢一个就会开出 seq 空洞。`session/subscribed` 是每代的重设基线，其 `lastSeq` 约束着它前后的帧。`approval/requested` 与 `question/requested` 是用户必须回答的提示的唯一副本，而每个 `approval/resolved` / `question/resolved` 都结算一个各不相同的待决项。

`session/queue` 与 `session/jobs` 本来也是可靠的——两者都是有文档的整快照帧，客户端是替换而非累积，而客户端自己的实例化前缓冲区已经按会话对 `session/queue` 做压缩。它们仍被排除，因为基准测试测得这两类**没有**任何可省下的帧：两者都在罕见的用户或注册表动作上触发，而非每事件触发。合并它们会把一次任务的 `running -> stopping -> killed` 推送序列压成只剩 `killed`，用一个可见的状态转换换来毫无可测收益的结果。

## 测试

`api-proxy-projections.spec.ts` 新增三个用例：未投递的帧收敛为每键一个存活帧，携带最终 seq 上的最终值；键绝不跨会话或跨单元合并；以及在旁边的投影被合并的同时，每个 `session/event` 仍以连续 seq 到达。原有的按单元广播用例现在在各次追加之间排空，这正是实时 agent 循环产生的节奏，也是其契约所针对的节奏；两个 `session/jobs` 生命周期用例未经修改即通过，这是任务状态转换未被触动的直接证据。

实时投递的正确性未变：`session/event` 帧永不设键，因此[实时事件窗口恢复](../bug-fix/2026-08-25-live-event-window-recovery.zh.md)中出错窗口的重新打开仍能看到每一个实时帧。

同一基准、同一机器上的改动后测量：

| | 之前 | 之后 |
|---|---|---|
| 扇出毫秒，8 流，1,320 事件突发 | 348 | ~24（不再随流数增长） |
| 投递帧数，8 流，paced | 22,720 | 13,760 |
| 投递帧数，8 流，事件循环阻塞 | 22,720 | 10,576 |
| 帧字节数，8 流，paced | 7,517 KB | 5,854 KB |
| 帧序列化毫秒，8 流，paced | 73.4 | 35.8 |

`paced` 行在每个回合后让出到宏任务队列，这正是实时 agent 循环的追加方式；`blocked` 则同步追加整个突发，这是繁忙主机事件循环所产生的形态。两者框定了任何队列策略所能节省的上限，而即使在 paced 情形下合并也去掉了 74% 的投影帧，因为一个回合内的事件会在流排空之前多次重算同一批单元。

## 备选方案

**按会话记忆化 `resolveSessionPreset`。** 依据测量被否决，且基准测试为此保留了一个常设用例。在真实机器最大的日志上（1,727 事件，最坏情况：完整反向扫描）解析耗时 15µs，在普通日志上为 0.07µs；一次覆盖 1,562 个会话的整目录 `session.list` 耗时约 64ms，其中解析占 0.12ms——**0.19%**。它完全不出现在 mux 热路径上。按会话记忆化还必须在 `agent-preset/selected` 上失效，而那正是该函数存在的意义所在，因此它换来的是千分之二的收益和一个组合陈旧的隐患。

**同样上提每流的 `session/created` 与任务监听器。** 它们在每次会话创建或注册表提交时运行，而非每事件；且任务监听器闭包持有开流时读取的 `ctx.get('jobs')`，因此在 jobs 服务组合之后打开的流仍能看到它。上提会把该读取冻结在网关构造时，却换不来任何实测收益。

**缓存 `ctx.agents` 服务引用以跳过 Context 代理。** 属性代理对拓扑敏感，缓存的引用会在重新组合后继续存活。把查找改为惰性，可在不触动解析语义的前提下去掉四分之三的调用。

**为队列设界并在压力下丢弃。** 字节或长度上界需要一套"丢什么"的策略，而唯一可安全丢弃的帧正是取代键已经移除的那些。会丢弃 `session/event` 的上界，会把可见故障变成静默故障。

## 影响

每事件的主机开销现在与连接的消费者数量无关：打开第二个标签页不再让网关在每个会话事件上的工作翻倍。仍随流数增长的是 SSE 处理器中的每流序列化，以及每流的订阅基线（每次打开 1,561 个 `session/subscribed` 帧，约 16ms），二者都是"有 N 个客户端"这一事实所固有的。

合并是真实的行为变更，而非纯粹的优化：客户端不再观察到那些在投递前就被取代的中间投影值。它最终停在相同状态，因为存储无论如何都会丢弃更低的 seq，但想从线路上拿到完整取值历史的消费者在这里拿不到了。任何需要该历史的东西都需要一个持久事件，而[投影设计](../../proposed/architecture/2026-07-27-session-projection-and-command-log.zh.md)对模型可见的事实本就有此要求。

本分支未处理的实测开销是每流订阅基线，以及[会话列表加载性能](../bug-fix/2026-08-25-session-list-load-performance.zh.md)所报告的主机内容检索。
