# Agent Note: JSON units coalesce publishes and price legibility per unit

Status: implemented

[English](2026-08-19-json-unit-publish-coalescing-and-format-ceiling.md) | 中文

## Problem

json 后端在每个写入原语上都会以美化格式重新发布整个单元文件，而 `dsh-storage-json` 当初是按设置类单元来权衡这一代价的。会话投影缓存打破了该假设：`session_projcache.json` 每个会话一行，因此随用户的整个会话历史增长，而它的插件会在每个节流触发点（`writeEveryEvents`/`writeIntervalMs`）以及两个强制点写入一次检查点。在这台工作站上，实际文件为 723 行、2.59 MB，一次检查点约需 19 ms 的序列化加临时文件写入、fsync 与 rename——这个单次写入成本随用户历来做过的所有事情增长，而非随正在写入的那个会话增长。这里有两个互相独立的放大因子：对无人阅读的文件调用 `JSON.stringify(document, null, 2)`，以及即便多个提交同时未决也每个提交一次物理发布。

## Decision

**可读性按单元计价，而不是按后端计价。** `serialize` 接收 `FormatPolicy`：紧凑文档不超过 `Config.prettyPrintMaxBytes`（经 `z.natural()` 校验，默认 65_536 字节）时以美化格式发布，超过则以紧凑格式发布。该默认值比维护者会打开的单元（`workspace.json`，约 5.9 KB）高两个数量级，比机器写入的缓存（`session_projcache.json`，兆字节级）低两个数量级。`parse` 未改动，两种格式都能读取，因此调整上限无需迁移：下一次发布即以新格式重写文件。希望保留旧行为的组装把上限设到大于其最大单元即可；`0` 表示全部使用紧凑格式。

**发布会被合并，但绝不重排。** `JsonKvUnit` 用一个发布循环取代了每个提交启动一次写入。每个写入方法先把变更应用到具有最终决定权的内存状态，登记一个撤销回调与一个等待者，并把单元标记为脏；循环取走此刻已登记的全部等待者，对当前状态序列化一次，原子写入，并一次性结算整批。写入进行中到达的提交由下一轮迭代结算，因此 N 个相互重叠的提交只需两次整文件写入，而不是 N 次。后端约定未变：顺序仍属于调用方，被等待的调用仍然只在包含其请求状态的持久文件落盘后才完成——因为它所属的那一批是在该次发布序列化之前取走的。若序列化结果与该单元上一次发布的字节相同，则跳过写入：介质上已经是那份文件。

**失败后内存依然等于介质。** 回滚从各写入原语移入发布器：一次失败的发布会把自最后一份持久文件以来应用的所有变更按由新到旧撤销——包括失败的那一批以及排在其后的提交——并让它们的调用方全部拒绝。任何被拒绝的内容都不会搭上后续发布。`writeAtomic` 未改动，持久性仍由临时文件写入 + fsync + rename + 目录 fsync 定义，`close()` 在释放单元前排空发布器。

## Measurements

在同一个进程中，让改动前与改动后的 `openJsonUnit` 分别针对实际 `session_projcache.json` 的独立副本（723 行，美化格式 2,585,922 字节）运行，并直接对 `putRecord` 计时：

| | 之前 | 之后（默认上限） |
| --- | --- | --- |
| 发布字节数 | 2,585,922 | 1,200,468（-53.6%） |
| 顺序检查点写入，10 次均值 | 19.64 ms | 9.00 ms |
| 内容相同的重新发布 | 19.03 ms | 4.28 ms，无写入 |
| 10 个并发提交 | 158.42 ms，10 次写入 | 7.58 ms，1 次写入 |

每种变体都重新打开自己发布的文件并读回全部 733 行。上限判定需要一次紧凑序列化，因此保持美化格式的单元每次发布会序列化两次；在默认值下该开销以 64 KiB 为界，而强制让 2.59 MB 的单元使用美化格式实测每次写入 19.28 ms，之前为 19.64 ms。

## Testing

`packages/storage/storage-json/tests/publish.spec.ts` 通过包装 `rename` 统计物理发布次数：中间没有 await 的一批提交只发布一次；发布进行中产生的提交恰好增加一次后续发布；每个被等待的写入都能在其完成时所依赖的文件里找到自己的记录；内容相同的重新发布不写盘；一批提交不留临时文件残留且重新打开后完好；失败的发布会回滚排在其后的提交。同一文件也钉住两种格式：超过上限用紧凑格式，低于上限用美化格式，两者经 `parse` 得到相同状态。`tests/json-backend.spec.ts` 保留共享的 `runKvBackendContract` 套件，并新增 `prettyPrintMaxBytes` 的校验与默认值断言。

## Alternatives considered

**直接放弃美化格式。** 只需一行改动，却删掉了该后端存在的理由：`workspace.json` 与设置类单元确实由维护者打开阅读。代价是按单元支付的，因此决策也应按单元作出。

**提供 `format: 'pretty' | 'compact'` 开关。** 按根目录的模式无法区分共享同一发布根目录的那两个单元；下推到按单元则意味着每个领域拥有者都要决定一个描述符字段。文档大小才是这个选择真正依赖的事实。

**发布前设置防抖窗口。** 定时器可以合并单次发布器无法合并的提交，但每个调用方都在等待持久化，因此该窗口是每次写入都要付的额外延迟；在领域层写入链（发出下一次写入前会等待上一次发布）之下，它什么也合并不了，只会让每次检查点更慢。连同它所需的可调项一并否决。

**在字节持久化之前就完成提交。** 这是折叠投影缓存串行检查点最省事的做法，却为了照顾一个消费方而破坏后端约定中面向所有消费方的持久性条款。

**按记录或基于追加的文件。**[领域 KV 存储 Agent Note](../../proposed/architecture/2026-07-24-domain-kv-storage-and-workspace.md) 已针对该后端否决了“追加 + 压实”方案；整文件重新发布正是让文件保持当前净状态的原因。该记录的格式条款写的是 `JSON.stringify(…, null, 2)`，本决策把它收窄到上限以下的单元。

## Consequences

一次投影缓存检查点的耗时约减少 42%，字节数减少 53.6%，而一批相互重叠的缓存写入只需一个文件而非每个会话一次。收益仍随会话总数增长，因为文件依然整体重新发布——由 storage-domain 的路由决定哪些单元应改用 SQLite，本次改动并没有把 json 后端变成规模问题的答案。

`session_projcache.json` 现在是一整行紧凑 JSON。此前用编辑器直接阅读它的人需要经过格式化工具，或为该根目录调高上限。

合并只对真正重叠的提交有效。领域层写入链在发出下一次写入前会等待上一次发布，因此仅通过 `ctx.storageDomain` 写入的消费方仍是每次写入一次发布；其收益来自格式上限与相同字节跳过。README 已记录这一点。
