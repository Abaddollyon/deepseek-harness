# Agent Note: 自适应历史事件窗口

Status: implemented

[English](2026-08-23-adaptive-history-event-windows.md) | 中文

## Problem

历史 API 按可见消息限制分页，而持久化分页统计原始会话事件。一次流式 assistant 响应可能在两条可见消息之间放入数百或数千个 chunk 事件。因此，每次只读取 `maxMessages` 个原始事件会让一个历史页触发多次重复扫描；对于每次有界读取都必须解析完整工件的顺序持久化介质，代价尤其明显。

## Decision

`SessionPersistence.readTail(id, beforeSeq, limit, signal?)` 返回独占序号位置之前至多 `limit` 个有效事件，并报告是否仍有更早事件。默认实现通过 `readFrom(id, 0)` 派生该页，因此所有后端都获得此操作，而无需立即实现存储专用版本。

分离状态下的 `session.history` 从至少 256 个原始事件开始读取。如果窗口未到达请求页所需的最早消息组，API 会向前移动游标，并把下一次读取上限翻倍，单次最多返回 16,384 个事件。可见消息配额和来源事件分组语义保持不变。

未以 `turn/end` 结束的尾部会执行一次按 id 的完整检查，从而保留内存中的中断恢复结果。尾页投影快照必须结束于有界历史来源的同一事件；投影快照陈旧或不可用时，也会执行一次按 id 的完整检查以折叠投影。已附加会话继续读取其内存事件数组。

## Alternatives considered

**每次原始事件读取都使用可见消息上限。** 拒绝，因为流式事件密度与消息数量无关，并会强制顺序工件反复扫描相同区域。

**每次都完整检查分离日志。** 拒绝，因为即使调用方只请求较小的尾页，也会实体化并保留完整事件日志。

**使用一个固定的大事件窗口。** 拒绝，因为足以覆盖流式密集历史的大小会让普通历史过度读取，而较小的固定值仍会在更密集的流中重复扫描。

## Consequences

普通分离页通常通过一次 256 事件读取完成；流式密集页会按几何级数扩大窗口，而不是按消息大小的原始窗口前移。每次读取返回的事件仍以 16,384 为上限，但默认持久化实现仍可能扫描完整顺序工件。以后可以加入存储专用的尾部寻址而无需改变 API proxy。

响应事件区间、`hasMore`、消息配额、压缩来源分组、投影切点和中断恢复行为保持不变。聚焦的 API proxy 测试固定了初始窗口、几何扩展、精确的 `beforeSeq` 分组、按 id 的投影回退以及不列举会话全集。
