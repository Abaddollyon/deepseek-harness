# Agent Note: Keyed projection-cache rows and watermark-gated checkpoints

Status: implemented

[English](2026-08-20-projection-cache-keyed-rows-and-watermark-checkpoints.md) | 中文

## 问题

投影缓存以单个文档持久化。每次检查点都会重写整个文档，因此写入成本随记录总量而非发生变化的会话增长——实测部署使用一个 1.6 MB 的文档，仅一个轮次结束就足以触发重写。

脏状态计数统计了错误的对象。每个 *已提交事件* 都会推进计数器，因此流式轮次会为完全没有移动任何投影的事件反复启用检查点；计数和间隔限流原本用于抑制一个本就不该触发的信号。

更糟的是，流中检查点路径采用了持久性屏障：它先对注册表截点生成快照，再刷新会话日志，然后写入缓存行，从而保证崩溃可能使缓存落后于日志，但绝不会领先。刷新日志恰恰是流式轮次不得执行的阻塞工作，而它却运行在热路径上。

## 决策

**SQLite 中的键控行。** 缓存组合到 SQLite 存储上，每个会话对应一行，因此检查点只写入发生移动的会话。

**统计投影移动，而非事件。** 每会话状态跟踪 `lastChangedSeq`，即该会话最近一次已计数的投影变更序列，注册表的每单元变更信号按序列去重（一个事件可以移动多个单元）。只有投影状态引用发生变化，检查点才会更新，因此限流现在抑制的是一个有实际含义的信号。

**流中不刷新。** `checkpoint` 写入缓存行时不会强制排空日志的延迟写入，并且有意反转不变量：缓存可以短暂地 *领先* 已存储日志，`coldSnapshot` 会检测超前的行并从 seq 0 开始重放。强制执行点（`turn/end`、分离）维持原有顺序；只有流中路径用低成本恢复换掉屏障。

## 备选方案

**按会话前缀对文档分片，而不是迁移到 SQLite。** 否决：分片会选择一个对小型和大型记录集都不合适的扇出常量，而且是在拙劣地重新实现键控存储。SQLite 存储已经拥有键控持久化行，组合到它上面让缓存继续作为消费者，而不是成为第二个存储引擎。

**保留刷新屏障，并使其异步。** 否决：异步屏障并不是屏障。写入要么等待——这正是要消除的成本——要么失去顺序保证；在后一种情况下，诚实的设计应明确缓存可能领先，并在读取时处理，这正是 `coldSnapshot` 重放所做的事情。

**写入时通过与日志尾部比较来检测超前行。** 否决：这只是换了一种形式的刷新，因为获知持久化尾部就意味着必须等待它。

## 影响

检查点的成本现在与单个会话成正比。崩溃可能使缓存行领先于已存储日志；冷读取会检测这种情况并从 seq 0 开始重放，以较慢的冷路径换取永不阻塞流式轮次——而且重放能够保持正确性，相比之下，先前设计的成本是无条件的。强制检查点保持不变，因此大多数读取所需的持久值（轮次结束时的值）仍会在 `turn/end` 落盘。
