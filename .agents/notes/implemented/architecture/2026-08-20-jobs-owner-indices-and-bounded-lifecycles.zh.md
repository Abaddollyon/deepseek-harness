# Agent Note: Owner-indexed background jobs with bounded retention and teardown

Status: implemented

[English](2026-08-20-jobs-owner-indices-and-bounded-lifecycles.md) | 中文

## 问题

本地作业注册表用一个扁平的 `store` 保存它曾接纳的每个作业，并通过扫描该存储回答所有查询。`list(caller)` 遍历整个存储以按所有者筛选，接纳计数也采用同样方式统计活动工作，因此，运行许多会话的主机在 GUI 持续访问的路径上需要付出 O(sessions × jobs) 的代价——mux 基线在每次打开流时为每个会话推送一个 `session/jobs` 帧，而无所有者作业的扇出会对每个订阅者重复此过程。

该存储没有任何边界。终态记录连同其缓冲输出会永久保留，因此长期运行的主机会不断累积已结束的作业及其载荷，直到进程退出。

拆卸同样没有边界。`disposeOwned` 和 `disposeAll` 会取消所属记录，然后无期限地 `await Promise.all(job.settled)`；只有 *抛出异常的* `cancel()` 才会被强制标记为失败。生产者契约已经承认这一缺口——取消操作返回但没有结束 `done`，与缓慢停止无法区分——因此一个不配合的生产者就会卡住代理释放，并进一步卡住主机关闭。这就是中断调查中的 D9。

最后，作业完成通知会在其唤醒预算内无条件唤醒空闲的所有者。人类按下停止后，所有者处于空闲状态，因此随后结束的作业会在用户刚刚结束的会话上开启一个新轮次——这与[cancellation-convergence note](../bug-fix/2026-08-20-cancellation-convergence-across-the-agent-tree.md)中记录的子代理结束通知缺陷具有相同形式。

## 决策

**按所有者建立索引，而不是扫描。** `ownedJobs: Map<string, Set<TrackedTask>>` 按所有者的 *session id*（而非确切的 `Agent` 对象）对记录分桶，因此具有相同 id 的调用者能看到当前所有者的作业，而需要确切所有者的查询（接纳计数、所有者释放时的排空）会按对象身份筛选该桶。`unownedJobs` 是共享桶。`list` 按注册顺序合并调用者的桶和无所有者桶，而不是筛选全部记录。

**维护接纳计数，而不是重新统计。** `activeCounts: Map<Agent | undefined, number>` 保存每个确切所有者的活动（`running`/`stopping`）计数，并以 `undefined` 键表示无所有者桶。注册时递增计数，首次有效结束时递减计数，因此接纳操作不再访问存储。

**限制终态保留量。** `settledJobs` 是一个按结束顺序排列、仅保存终态记录的集合，`maxSettledJobs`（经过验证的 `Config`，默认值 256）从头部逐出记录。逐出会从每个索引中删除记录、释放其缓冲输出，并通知每个受影响所有者的观察者，因为逐出会改变 `list` 的返回结果。活动作业绝不会被逐出——该集合只保存终态记录，因此此上限不会影响正在运行的工作。

**限制拆卸时间。** `teardownGraceMs`（经过验证的 `Config`，默认值 5000）限制等待结束的时长。宽限期过后，记录会被强制结束为 `failed`，拆卸继续进行且不再等待该生产者，这与抛出异常的取消分支已有的语义完全一致。

**让完成唤醒感知停止状态。** `tool-jobs` 通知在消耗唤醒次数前查询所有者最新的持久化 `turn/end`；当该结束是由用户导致的中止时，通过不会唤醒的 `inject` 交付。通知仍会进入收件箱，只是不再重新开启轮次。

## 备选方案

**用确切的 `Agent` 对象作为所有者桶的键。** 否决：Agent 被替换的会话（冷恢复、预设切换）会使其作业困在无法访问的桶中。session id 是调用者实际持有的持久身份；只有查询要求精确性时才按对象身份筛选，代码也在该字段处明确说明了这一点。

**按时间或缓冲总字节数限制保留量。** 本次变更不采用：计数上限的行为可由读者根据工具说明预测，而且每次读取的输出载荷已有边界。如果部署报告存在压力，仍可增加字节上限。

**立即强制将无法结束的生产者标记为失败，而不是等待宽限期。** 否决：缓慢但正确的停止——处于 SIGTERM-to-SIGKILL 窗口的子进程——才是常见情况，为追求一毫秒而将其报告为失败并不符合事实。

**只依靠唤醒预算处理停止后的唤醒。** 否决：预算限制的是一次突发可以消耗 *多少次* 唤醒，而不是唤醒本身是否正确。人类停止后，正确次数是零，持久化 `turn/end` 正是作出该判断的事实依据。

## 影响

接纳和列出操作分别为 O(1) 和 O(owned + unowned)；两者都不随记录总量增长。读取一个已逐出的结束 id 会得到未知作业——这是调用者可以观察到的行为变更，已在配置字段上记录，也是逐出操作会通知观察者而非静默修改的原因。拆卸现在能在有限时间内完成，并将卡住的生产者报告为 `failed` 而不是一直挂起，因此代理释放不再会被单个作业阻塞。人类停止后才结束的作业不再重启该会话。
